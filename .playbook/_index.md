# Playbook — Project Map & Session Rules

## What This Project Is

This repo builds and maintains **Playbook** itself: the `create-playbook` CLI, the
`@bogsp/playbook-software-library` npm package, and the domain-agnostic template
source that `create-playbook` scaffolds into consuming projects. It is not a
project that *uses* Playbook for an app — it is the tooling and templates that
other projects install.

Two Playbook worlds exist side by side in this repo, and they must not be confused:

| Path | What it is |
|---|---|
| `.playbook/` (this folder, dotted) | The **meta-pipeline** — governs AI sessions working on this repo's own code and templates |
| `playbook/.playbook/`, `playbook/docs/` (no dot) | The **template source** — the deliverable that gets copied into `packages/create-playbook/templates/` and scaffolded into other people's projects |

Never edit files under `playbook/` as if they were this repo's own planning docs —
they are product source, not meta-pipeline state.

**Kit files track this repo's own state.** `.playbook/kit/` holds current phase,
open questions, active tasks, and the append-only history — same discipline as any
Playbook project, applied to this repo's own development.

**`playbook/` is the deliverable.** It is read-only from the perspective of "what
should I edit to fix my own workflow" — it's the output, not the tool.

**Nothing changes without a human deciding.** Same rule as every Playbook project:
AI flags ambiguity and waits, especially for anything that changes the shipped
templates or the CLI's public behavior.

## Session Start

Read this file first, every session — it is the single entry point.

**Resuming work:** attach this file together with the kit files below in one message. On tools without a hard attachment or message-size limit (Claude, Gemini, and most current tools), this is all you need to align accurately.

- `kit/01-process.md` — current phase, active goal
- `kit/04-progress.md` — append-only history (kept lean by regular archiving)
- `kit/05-kanban.md` — active tickets (K-IDs), if any are open

**If your tool limits what you can attach at once:** send this file + `01-process.md` + `04-progress.md` first — that alone is enough to resume for most sessions.

**Then load whatever is relevant to the task:**

| Task | Also load |
|---|---|
| Editing the CLI | `packages/create-playbook/README.md`, the file(s) under `lib/` being touched |
| Editing the library | `packages/playbook-software-library/CONTRIBUTING.md`, `CHANGELOG.md`, `README.md` |
| Editing template source (`playbook/`) | The specific file under `playbook/.playbook/` or `playbook/docs/` being changed; check for a sync-check finding in `.playbook/kit/_refs/` first |
| Resolving an open K-ticket | `.playbook/kit/02-exploration.md` for related decisions |
| Unsure what frontmatter shape a file should carry | `.playbook/maintenance.md` — applies the Frontmatter Tiering Rule to this repo; canonical definition is `playbook/.playbook/maintenance.md` |

Confirm what you have loaded. Then wait for instruction.

## AI Behavioral Rules

### Frontmatter Standard

Every planning document, kit file, and generated artifact in this repo uses this
frontmatter block — no separate `# Title` / `# File:` comment header above it:

```yaml
---
file: '[full path from repo root]'
responsibility: '[one line — what this file holds, and nothing else]'
ai_instructions: '[how AI should read or update this file]'
archive_rule: '[when/how content moves to _archives/, or N/A]'
---
```

The `file:` field is the single source of truth for a document's filename and path.
Do not duplicate it as a heading comment.

Which fields beyond these four a file also carries — and whether it needs the
deep-module header — is governed by the Frontmatter Tiering Rule. Canonical
definition: `playbook/.playbook/maintenance.md`. Applied to this repo's own
files: `.playbook/maintenance.md`. Do not restate the rule here.

### Rules

1. Never edit `packages/create-playbook/templates/` directly — it is generated by `node build.js`. Edit the `playbook/` source, then rebuild.
2. Never edit `playbook/.playbook/` or `playbook/docs/` files casually — they are the shipped product. Treat changes as product changes: state what changes for every future scaffolded project.
3. Never add a new integration, solution, or concern to `packages/playbook-software-library/` without meeting the bar in its `CONTRIBUTING.md` (rules stated as must/never, failure modes explicit, no framework assumptions).
4. Never bump a version in `package.json` without a matching `CHANGELOG.md` entry.
5. Keep `.playbook/kit/01-process.md` and `04-progress.md` current — these are this repo's own working memory, same discipline this repo prescribes for every other Playbook project.
6. Flag before resolving any open architectural decision in `05-kanban.md` — it requires explicit human sign-off, not silent resolution.
7. When editing a file that exists in two places (root `.playbook/` vs `playbook/.playbook/`), confirm which one is intended before touching either — they serve different purposes and must not drift back into being copies of each other.
8. Run `pnpm lint` / `biome check` conventions (see `biome.json`) — this repo has no separate `docs/code-standards.md`; Biome config is the standard.
9. No planning document, kit file, or template change proceeds without checking this file's Structure section is still accurate afterward.
10. Every generated file uses the standardized frontmatter block above — never a separate `# File:` comment header.
11. Every file's frontmatter fields beyond the four-field floor follow the Frontmatter Tiering Rule (`.playbook/maintenance.md` for this repo, canonically `playbook/.playbook/maintenance.md`) — update frontmatter in the same pass any file is otherwise touched; if a phase leaves files untouched, reconcile them together at the end of that phase.
12. Fold any prior `In Progress` entry in `04-progress.md` into a `Decided`/`Completed` note in the same edit that adds a new one — only one `In Progress` entry should exist in the file at any time.

### When Something Is Unclear

Stop all work. Flag using this exact format:
`Categories: underspecified | missing-contract | undeclared-dependency | architectural-decision | ambiguous-behavior | template-vs-meta-ambiguity`

`template-vs-meta-ambiguity` is specific to this repo: use it whenever it's unclear
whether a requested change belongs in `.playbook/` (this repo's own state) or
`playbook/` (the shipped template).

### Never Do These

- Edit `packages/create-playbook/templates/` by hand
- Treat a change to `playbook/` as a private, low-stakes edit — it ships to every future project
- Resolve an open K-ticket architectural decision without human review
- Let this file's Structure section go stale
- Copy content between root `.playbook/` and `playbook/.playbook/` to "keep them in sync" — they are intentionally different documents now
- Add a `# Title` / `# File:` comment header above the frontmatter block
- Invent a frontmatter shape outside the Frontmatter Tiering Rule
- Leave more than one `In Progress` entry standing in `04-progress.md`

### Expansions

This repo does not currently run any pipeline expansions (audit, video-insights) on
itself. If one is ever declared, it follows the same rule as any Playbook project:
declared in `kit/01-process.md`, advanced only after human review.

### When Something Breaks

1. **Name it** — what broke (CLI behavior, library doc, template drift).
2. **Isolate it** — is it in `packages/`, `playbook/`, or the meta kit files?
3. **Fix the source** — if it's a template drift, fix `playbook/` and rebuild; don't patch `templates/` directly.
4. **Verify** — for CLI changes, re-run the affected `create-playbook` command against a scratch directory.
5. **Log it** — add a Fixed entry in `.playbook/kit/04-progress.md`.

### Session End

Update these two files before the session ends or when context reaches 80% —
do not wait to be asked:

1. `.playbook/kit/01-process.md` — current phase and what is next.
2. `.playbook/kit/04-progress.md` — completions, decisions, fixes. Fold any prior `In Progress` entry into a `Decided`/`Completed` note before adding a new one.

**Then:**

3. Confirm this file's Structure section still matches the repo.
4. If any `playbook/` template file changed, note whether `pnpm build` (in `packages/create-playbook/`) still needs to run.
5. Confirm every file touched this session has frontmatter matching its tier (`.playbook/maintenance.md`, canonically `playbook/.playbook/maintenance.md`) — fix before logging progress, not after.
