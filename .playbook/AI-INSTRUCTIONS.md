# AI Instructions — This Repo

Load this file at the start of every session working on the Playbook pipeline repo
itself. This is not the generic template — it governs work on `create-playbook`,
`@bogsp/playbook-software-library`, and the `playbook/` template source.

## Session Load Order

1. `.playbook/README.md`
2. `.playbook/AI-INSTRUCTIONS.md` — this file
3. `.playbook/_index.md`
4. `.playbook/kit/01-process.md`
5. `.playbook/kit/04-progress.md`
6. `.playbook/kit/05-kanban.md`

**Load based on the task:**

| Task | Also load |
|---|---|
| CLI work (`packages/create-playbook/`) | `packages/create-playbook/README.md`, relevant `lib/*.js` |
| Library work (`packages/playbook-software-library/`) | `CONTRIBUTING.md`, `CHANGELOG.md`, `README.md` in that package |
| Template source work (`playbook/`) | The specific file being changed; check for a sync-check finding in `.playbook/kit/_refs/` first |
| Resolving an open K-ticket | `.playbook/kit/02-exploration.md` for related decisions |

Confirm what you have loaded. Then wait for instruction.

## Frontmatter Standard

Every planning document, kit file, and generated artifact in this repo uses this
frontmatter block — no separate `# Title` / `# File:` comment header above it:

```yaml
---
file: '[full path from repo root]'
responsibility: '[one line — what this file holds, and nothing else]'
ai_instructions: '[how AI should read or update this file]'
archive_rule: '[when/how content moves to _archives/, or N/A]'
---
```

The `file:` field is the single source of truth for a document's filename and path.
Do not duplicate it as a heading comment.

## Behavioral Rules

1. Never edit `packages/create-playbook/templates/` directly — it is generated by `node build.js`. Edit the `playbook/` source, then rebuild.
2. Never edit `playbook/.playbook/` or `playbook/docs/` files casually — they are the shipped product. Treat changes as product changes: state what changes for every future scaffolded project.
3. Never add a new integration, solution, or concern to `packages/playbook-software-library/` without meeting the bar in its `CONTRIBUTING.md` (rules stated as must/never, failure modes explicit, no framework assumptions).
4. Never bump a version in `package.json` without a matching `CHANGELOG.md` entry.
5. Keep `.playbook/kit/01-process.md` and `04-progress.md` current — these are this repo's own working memory, same discipline this repo prescribes for every other Playbook project.
6. Flag before resolving any of the open architectural decisions in `05-kanban.md` (K-05, K-06, K-07, K-10) — they require explicit human sign-off, not silent resolution.
7. When editing a file that exists in two places (root `.playbook/` vs `playbook/.playbook/`), confirm which one is intended before touching either — they now serve different purposes and must not drift back into being copies of each other.
8. Run `pnpm lint` / `biome check` conventions (see `biome.json`) — this repo has no separate `docs/code-standards.md`; Biome config is the standard.
9. No planning document, kit file, or template change proceeds without checking `.playbook/_index.md` is still accurate afterward.
10. Every generated file uses the standardized frontmatter block above — never a separate `# File:` comment header.

## When Something Is Unclear

Stop all work. Flag using this exact format:
`Categories: underspecified | missing-contract | undeclared-dependency | architectural-decision | ambiguous-behavior | template-vs-meta-ambiguity`

`template-vs-meta-ambiguity` is specific to this repo: use it whenever it's unclear
whether a requested change belongs in `.playbook/` (this repo's own state) or
`playbook/` (the shipped template).

## Never Do These

- Edit `packages/create-playbook/templates/` by hand
- Treat a change to `playbook/` as a private, low-stakes edit — it ships to every future project
- Resolve an open K-ticket architectural decision without human review
- Let `.playbook/_index.md`'s Structure section go stale
- Copy content between root `.playbook/` and `playbook/.playbook/` to "keep them in sync" — they are intentionally different documents now
- Add a `# Title` / `# File:` comment header above the frontmatter block

## Expansions

This repo does not currently run any pipeline expansions (audit, video-insights) on
itself. If one is ever declared, it follows the same rule as any Playbook project:
declared in `kit/01-process.md`, advanced only after human review.

## When Something Breaks

1. **Name it** — what broke (CLI behavior, library doc, template drift).
2. **Isolate it** — is it in `packages/`, `playbook/`, or the meta kit files?
3. **Fix the source** — if it's a template drift, fix `playbook/` and rebuild; don't patch `templates/` directly.
4. **Verify** — for CLI changes, re-run the affected `create-playbook` command against a scratch directory.
5. **Log it** — add a Fixed entry in `.playbook/kit/04-progress.md`.

## Session End

Update these two files before the session ends or when context reaches 80% —
do not wait to be asked:

1. `.playbook/kit/01-process.md` — current phase and what is next.
2. `.playbook/kit/04-progress.md` — completions, decisions, fixes.

**Then:**

3. Confirm `.playbook/_index.md`'s Structure section still matches the repo.
4. If any `playbook/` template file changed, note whether `pnpm build` (in `packages/create-playbook/`) still needs to run.
